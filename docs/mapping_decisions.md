# Mapping decisions

Every OMOP conversion involves judgment calls that the source data cannot settle on its own. This file records each one, the reason for it, and what the data showed. Decisions marked **sensitivity candidate** are the ones the later study will vary to see how much downstream results depend on them.

Counts below come from DE-SynPUF Sample 1 and the OHDSI vocabulary release v20260829. They are regenerated by `run_all.R` into the `output` folder.

## Source overview

| Source file | Rows | Beneficiaries | Date range |
|---|---|---|---|
| Beneficiary summary (2008, 2009, 2010 stacked) | 343,644 | 116,352 | 2008 to 2010 |
| Inpatient claims | 66,773 | 37,780 | 2007-11-27 to 2010-12-30 |
| Outpatient claims | 790,790 | 85,272 | 2007-12-12 to 2010-12-31 |
| Carrier claims (1A and 1B) | 4,741,335 | 98,626 | 2008-01-01 to 2010-12-31 |
| Prescription drug events | 5,552,421 | 99,538 | 2008-01-01 to 2010-12-31 |

Every claim row in all four claim files links to a beneficiary. Only the inpatient and outpatient files contain claims dated before 2008.

## PERSON

**D1. One person per DESYNPUF_ID, demographics from the most recent yearly file.**
A beneficiary can appear in up to three yearly files, and in principle the synthetic data could disagree across years. In Sample 1 it never does. Sex, birth date, and race are identical across years for all 116,352 beneficiaries. The rule is kept as a safeguard and costs nothing.

**D2. Race and ethnicity both come from BENE_RACE_CD.**
Medicare records Hispanic as a race code (5) rather than a separate ethnicity field. Code 5 maps to ethnicity *Hispanic or Latino* (38003563) and race 0, since OMOP treats Hispanic as an ethnicity. Code 3 ("Other") has no matching standard race concept and maps to 0. Every other code maps to ethnicity *Not Hispanic or Latino* (38003564). Result is 7,660 persons (6.6%) with race concept 0, of whom 2,729 are Hispanic.

**D3. Persons without a valid birth date are dropped.**
OMOP requires year_of_birth. In Sample 1 no one is dropped for this reason.

## DEATH

**D4. Earliest death date across yearly files, one row per person.**
5,461 persons have a death date. Every death date falls on the first of a month, which reflects how the synthetic file was generated rather than real dates, so death timing is only accurate to the month. No claims start after a death date.

## OBSERVATION_PERIOD

**D5. Observation period from yearly file presence, ended at death.** (**sensitivity candidate**)
SynPUF has no enrollment start and end dates. This ETL starts each person on January 1 of the first year they appear and ends them on December 31 of the last year they appear, or on the death date if earlier.

In Sample 1 everyone appears in the 2008 file, so every period starts 2008-01-01. 110,891 persons (95.3%) are observed for the full three years.

Two observations show the cost of this simple rule.
1. **Coverage months are ignored.** 16,314 beneficiary-years (4.7%) report zero months of Part A and zero months of Part B coverage, yet the rule counts them as observed time. An alternative rule built from the coverage-month fields is the first planned variant.
2. **Some claims start before the period.** 224 inpatient and 312 outpatient claims begin in late 2007, before the January 1, 2008 start. Phase 2 must decide whether to drop those events, keep them outside the period (OMOP allows this, and the Data Quality Dashboard flags it), or start the period earlier.

## Type concepts

**D6.** Death records use type concept 32810 (*Claim*). Observation periods use 32880 (*Standard algorithm*), since they are derived by a rule rather than recorded directly.

## Hard-coded concept IDs

Every concept ID written into the SQL is listed in `reference/concept_constants.csv`. `run_all.R` checks each one against the loaded vocabulary for existence, expected name, expected domain, and standard status, and writes the result to `output/concept_constants_check.csv`.
